## 第 1 步 资料持久化

**目标**：大量资料录入一次，重启后不用重新上传；按内容哈希增量录入。

**做法**：没有用向量数据库，用「文件夹 + json/npy」（几百份资料、几万段的规模，numpy 直接算相似度就够快；少一个依赖，也更容易看懂）。`rag.py` 的 `FileStore` 负责存/读，`library_add()` / `library_load()` 在上层；以后换 LanceDB / Chroma 只需写一个方法相同的类替换 `FileStore`。资料存在 `library/`（不进 git），按 sha256 增量录入；BM25 每次载入时现场重建；存的嵌入模型名和当前不同时，载入时自动重算向量。在线体验版（`DEMO_MODE`）默认关闭持久化，开关是 `PERSIST_LIBRARY`。

**评测**：和改动前完全一样（全部 ✅，证据未命中仍是原来那 2 题）。

**坑**：逐个文件算向量和所有文件一起算，数值差约 1e-4（同一批里短段落会补齐到最长那段的长度），排名不受影响，不是 bug。

## 第 2 步 换嵌入模型

**目标**：原来的 MiniLM 最长只读 128 token，800 字的段落只看到开头。

**做法**：先做对比实验（4 个模型 × 4 种段落长度，只评检索、不调 DeepSeek，复用 eval_output.json 里的关键词）。e5-large 最好：21 道证据题「纯向量前 6」单文档 15→20、五份文档混成书架 13→18；Qwen3-0.6B 次之且更慢。**段落没有切小**：e5 下 800 字反而最好（300/500 字都更差），因为 e5 能读 512 token，800 字中文段落平均只有 200–300 token。`rag.EMBED_MODELS` 记录各模型的问题/资料前缀（e5 要 `query: ` / `passage: `），新增 `embed_query()`，`retrieve()` 只改了一行；本地默认 e5-large（环境变量 `EMBED_MODEL` 可改），在线体验版默认仍用 MiniLM。

**评测**：全部 ✅ 不变，证据未命中 2 → 1（只剩「生成部分用的是哪个预训练模型？」）。

**坑**：bge-m3 不在 fastembed 支持列表里（要装 PyTorch）；e5 算向量慢很多（约 6 段/秒，原来约 95 段/秒），好在有持久化，每份资料只算一次；题目少，1–2 题的差别不能说明问题。

## 第 3 步 中文分词

**目标**：BM25 原来把中文切成单字，资料多时噪声大。

**做法**：先查了各分词工具的维护情况（jieba 2020 年后停更，Python 3.12 上报 SyntaxWarning；rjieba 是 jieba 的 Rust 版，仍在更新，切法逐字相同；HanLP / LTP 太重），选 rjieba。对比 6 种切法（单字 / rjieba 普通 / rjieba 搜索 / 搜索+单字 / bigram / e5 分词器），rjieba 搜索模式最好：五份文档混成书架时，关键词检索证据排第 1 的 14→16、进前 6 的 18→20、MRR 0.734→0.838、最终混合@6 19→20（共 21 道），没有一道变差。只改了 `tokenize()`。

**评测**：全部 ✅ 不变。

**坑**：rjieba 普通模式会切出不一致的词，「坏了能免费修多久」的证据从第 1 掉到第 41；虚拟环境是 uv 建的，没有 pip，装包用 `uv pip install --python .venv/bin/python 包名`。

## 第 4 步 资料库管理

**4a 列表 + 删除**：侧栏列出已录入的资料（类型、文件名、段数），点 🗑 弹出居中的确认框，里面的红色「删除」才真删。
**4b 提问范围**：侧栏「提问范围」多选框，不选 = 全部资料；选了几份，提问、总结、Excel 统计都只看这几份（`rag.library_subset()`，每段记下 `doc` 编号，同名文件也分得开）；输入框提示写「只在「某某」里找」。

**评测**：全部 ✅ 不变；「一季度哪个产品卖出的数量最少？」错过一次，单独重问 4 次全对。

**坑**：

- 删除后上传框还记着那个文件，下一轮又会录回去，删除时要给上传框换个 key；
- Streamlit 的 markdown 自带 -16px 下边距，和按钮垂直居中一起用会错位；
- **改了 `rag.py` 要重启 Streamlit**，它只在启动时读一次；当时还发现两个旧进程一直在后台跑（`pgrep -fl streamlit`）；
- Streamlit 1.66 多选框：光标被挤到第二行；菜单开着时点清空 ⊗ 会点空。用 CSS 藏光标、固定高度、藏 ⊗，换成自己的「全部资料」按钮（试过改成单选，用户觉得不是想要的效果，所以保留多选框、自己修毛病）；
- DeepSeek 偶尔返回 503「Service is too busy」，评测里零星「暂时出错」不是代码问题。

## 第 5 步 接入 OCR

**做法**：PDF 逐页判断，读不出字的页用 pypdfium2 渲染成 144 dpi 图片，交给 rapidocr 认字，出处标「第 N 页（扫描识别）」；文字页照旧。中文行尾被截断的换行会接上（不然被拆在两行的词会被分词切错）。开关 `OCR_ENABLED`。eval 里扫描件题从「友好提示」改成要答对，另加 2 道。

**评测**：全部 ✅（原有 28 + 新增 7），3 道扫描件题都答对。

**坑**：有的扫描版 PDF 里的字是用线条「画」出来的，不是图片，PDF 里抠不出图，必须整页渲染；约每页 1.8 秒，20 页 40 秒。

## 第 5b 步 问题里点名资料（中途加的）

**起因**：问「第一个档案主要是讲什么」时，DeepSeek 不知道资料清单，「第一个」靠蒙；「档案」这个说法也没进总结模式，6 段引用里混进了别的资料。

**做法**：判断问题类型时附上带编号的资料清单（和侧栏顺序一致），DeepSeek 回答类似 `SUMMARY 1`、`CALC 2,3`，不多调用一次。规则是和用户商量定的「方案 A」，问题优先、只管这一问：点名了就只在那几份里找，只管这一问；页面提示「这次按你的问题，只看了：xxx」。写回答时也告诉模型「问题里说的资料指的是《xxx》」。eval 新增「书架」4 题。

**坑**：光靠提示词说「没点名就别写编号」不够稳，同一句「押金是多少？」一次没选、一次选了合同（temperature 0 也会变），所以加了程序检查（后来第三轮审查发现它太松，又重写了，见下面 N1）。

### 第 2 轮审查（第 5 步 OCR，11 条）+ 第 3 份「第二轮」（N1–N8）

- **OCR 一页失败只少一页**；`build_index()` 逐个文件 try；读取失败的上传文件按哈希记下，只试一次；
- **资料库不崩不丢**：manifest 写坏自动备份、提示重新上传；缺文件只跳过那一份；`FileStore.replace()` 原地替换；
- **水印扫描件**（扫描全能王每页角上印一行真文字）：`image_ratio()` 判断大图盖住半页以上也做 OCR；
- **处理版本号** `PIPELINE_VERSION`：旧资料打开时自动按新规则重新处理，段落没变就沿用向量（真实资料库升级 5 份 0.5 秒）；
- **中文错误提示** `explain_error()`：有密码、损坏、假 Word/Excel、网络问题分开说；
- **小测试** `tests/test_library.py`；
- **收尾**：OCR 内存 2.22GB → 1.77GB（最长边 1280，结果一字不差）；标题不和正文拼接；只剩 1 份资料时清空提问范围；固定 opencv / onnxruntime 版本；进度条「第 9 / 20 页」。

**坑**：我在项目说明里写过「旧扫描件不会重识别——已解决」，其实只解决了「0 段 + 重新上传」一种，说过头了，后来用 `PIPELINE_VERSION` 才真正解决；AppTest 点不到 `st.dialog` 里的按钮；pypdfium2 5.x 用 `get_bounds()`；假 docx 可能报 KeyError 而不是 BadZipFile。

### 第三轮审查（N1–N11）

- **N2 段落和向量错位**（这份之后所有资料的引用都会错位）：重新处理改成写带版本标记的新文件、最后一次性改目录；载入时检查段数 = 向量行数 = 目录记的段数；
- **N1 点名资料太松**（Grok 的 15 个没点名问题放行了 12 个）：改成本地先判断再发清单（`ORDINAL_RE` / `DESCRIBE_RE` / `name_words()`），宁可少认（没认出只是退回在全部资料里找；认错了，这一问会漏掉别的资料里的答案）；`_parse_pick()` 支持「DOC 1-3」；
- **N3** 封面页、PPT 页的真文字不再被 OCR 结果替换；**N4** 某页 OCR 失败在侧栏提示、下次打开重试一次；
- **N5–N11**：升级失败提示常驻、点名 0 段资料说清楚、同名文件失败记录不混、测试不依赖 `.env` 和模型（干净拷贝里全过）等。

**坑**：rjieba 会把资料名里的三字词切成「一字 + 两字」，按名字认资料时要注意；测试里替换 `staticmethod` 再放回去要从 `类.__dict__` 取；干净拷贝没有 models/ 时，页面一打开先下载 2.2GB 模型，AppTest 超时。

## 第 6 步 扩大评测（进行中，2026-11-04）

**做法**：

- 两套题都只在本地（`my_eval/`，不进 git）：**用户的 33 道**（Grok 帮忙整理，每道核对过原文、计算题用程序验算）和 **Claude 出的 13 道**（和前者重复的 3 道已换掉）；
- 在「测试书架」上答：5 份公开资料（NIST《AI 风险管理框架》、一份产业规划、一份教育类指南、两张数据表）录进单独的测试资料库，走和网页一样的录入 → 载入 → 提问；单份资料的题只看那一份（相当于提问范围），跨文档题看全部；
- `eval.py --real-only` 单独跑（题目和结果只在本地）。

**第一次结果**（5 份资料、258 段）：

| 题集            | 评测判定            | 人工复核后                                        |
| ------------- | --------------- | -------------------------------------------- |
| 用户的 33 道      | 26 通过、5 待复核、2 错 | **30 / 33**（5 道待复核其实都对，只是答案不在第一句；1 道判对其实是错的） |
| Claude 的 13 道 | 12 / 13         | 12 / 13                                      |
| 证据被检索到        | 20 / 23         | 漏掉的 3 道都是 NIST「中文问英文」                        |

**答错的 4 道和原因**：

1. 「从哪个国家或地区的**进口额最多**？」→ 没进统计模式，只看到 6 行里的 3 个国家；
2. 「水路周转量占全部的**百分之几**？」→ 两个数字都找到了，但提示词要求「片段里没有的就说没有」，模型不敢自己算（同类的「平均飞多少公里」又算了，时好时坏）；
3. 「核心产业规模目标是对东盟出口额的**几倍**？」→ 点名了那份产业规划就只在那一份里找，可答案还要用贸易数据表（第 5b / N1 的副作用）；
4. 「哪一项特征是其他特征的**基础**？」→ 中文问英文，检索没找到「Valid & Reliable is a necessary condition」。

**评测规则的漏洞**：第 4 题回答「没有提到哪一项是基础」，顺带列了一遍特征，命中了关键词被判 ✅。

**改进方案**（按顺序做，每条跑评测对比）：

1. 表格题一定带上程序算好的统计（带上是哪一行）；
2. 允许用片段里的数字做简单计算，写出算式和数字出处；
3. 先用一句话直接回答，再解释；
4. 点名资料不一刀切：还要用到别的资料时让 DeepSeek 一起选上；资料不多时名字命中也发完整清单；
5. 修评测规则：第一句就说「没有提到」的不算答出来；
6. 中文问英文的检索先记进已知问题。

### 改进 1：表格题一定带上程序算好的统计（2026-11-04）

- `describe_table()`：有一列能当名字（每行都不一样，如 国家和地区、指标、订单号）时，最大最小写明是哪一行；表不超过 `TABLE_RANK_ROWS`（15）行时附上每个数字列从大到小的排名；数字末尾的 0 去掉（39.8 不写成 39.80）。
- `answer()`：统计题照旧附全部统计；**其他问题检索到了某张小表的行，也附这张表的统计**。
- 结果：样本题原有 28 道全对（R5 单价恢复、BART 这次也对）、新增 12 道全对；真实资料题用户 33 道 26 → 27 通过（另 4 道 🔍 人工看都对），Claude 13 道 12 → 13（「进口额最多」修好）。
- **坑**：① 一开始只要检索到某张表的行就附整张表的统计，30 行的销售明细也附上了，里面「按产品分组的单价合计」把「R5 单价多少」带偏成「文档只给了合计」，改成只附小表；② 统计里写成 39.80，模型照抄，评测拿 39.8 对不上，顺手改了数字格式；③ 「哪一项特征是基础」以前被评测规则的漏洞误判 ✅，这次如实判 ❌（改进 5 会修这个漏洞）。

### 换思路：靠「理解」和「找到」，不再一道道修题（2026-11-04）

- **起因**：作者发现「题越多、错越多，靠手动修跟不上」，而且修一道可能弄坏另一道（改进 1 时 R5 单价就被弄错过）。讨论后定下：溯光要做的是**精准理解用户的诉求，再准确找到原文依据**；错题几乎都出在这两环。
- **评测升级**（`eval.py`）：给 46 道练习题标上标准答案（类型、需要的每段原文、该看的资料，放在本地 `my_eval/labels.json`）；新增「理解」「资料范围」「找到原文」三项指标；`--repeat 3` 每题跑 3 次；修了判分漏洞（第一句就说「没提到」的不再算答对，原改进 5）。
- **基准**（还没做「理解」这一步，每题 3 次）：

| 指标     | 用户的 33 道 | Claude 的 13 道 |
| ------ | -------- | ------------- |
| 理解（类型） | 96%      | 77%           |
| 资料范围   | 50%（3/6） | 100%          |
| 找到原文   | 85%      | 89%           |
| 答对     | 84%      | 100%          |

- **卡在哪**：① 计算题要两段原文，一次检索只找到一段（「坐飞机平均每人飞多少公里」0/3）；② 点名了一份资料就只在那一份里找（「东盟出口额的几倍」范围 0/3）；③ 中文问英文时好时坏；④ 「比较排名」题被当成普通查找（靠改进 1 的表格排名歪打正着答对）；⑤ 3 道题答案都对，但没先直接回答，被标「待复核」。

### 「理解」这一步（2026-11-04）

- **做法**（`rag.py`）：`understand()` 用一次调用（JSON 输出）代替原来的「判断类型」+「改写关键词」，DeepSeek 调用 3 次 → 2 次。输出：类型（查事实 / 比较排名 / 计算 / 总结 / 对比 / 闲聊 / 介绍）、在问什么、要找的每样信息（各带中英文关键词）、资料范围、怎么得出答案。`retrieve_targets()` 按每样信息分别检索再轮流合并（最多 12 段）。资料不超过 `DOC_LIST_FULL`（30）份时，点名也附完整清单，让模型把还需要的资料一起选上。回答规则加了「第一句直接回答」「可以用片段里的数字做简单计算，写出算式和出处」。

## ⏸ 暂停（2026-11-04）：方向调整为「程序为主、模型为辅」

**作者的想法**：溯光的价值要体现在我们自己写的程序上，「主要靠本地、在程序上跑通」，而不是把问题转给大模型、它说什么就是什么。程序做的每一步都能解释、能复现，这和「每句话都能溯回原文」的初衷一致。
